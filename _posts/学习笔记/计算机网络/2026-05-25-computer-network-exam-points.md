## 物理层

### 1.循环冗余检验 (CRC)

错误检测技术。它的核心目标是确保数据在传输过程中保持**完整性**，即接收端收到的数据与发送端发出的数据完全一致。

![image-20260108154927174](/assets/images/study-notes/computer-network-exam-points/01-image-20260108154927174.jpg)

#### 1.1 发送什么

信息位：发的数据 被除数

生成多项式G（x）：一个预先约定好的、不可变的二进制**除数**

冗余多项式R(x):余数（校验码） 加在信息位后

##### 步骤：

**信息位为除数（后面加最高次数个0！）**

**生成多项式转为被除数**

**开始除 异或：同0不同1**

**余数位数若不足最高次数：在前面补0**

**放在信息位后一起传输**

![image-20260108154951860](/assets/images/study-notes/computer-network-exam-points/02-image-20260108154951860.jpg)



#### 1.2 接收端错误检验

接收端收到 k+r位的数据帧 T 后，会用同样的生成多项式 G对其进行模 2 除法。

如果**余数为 0**： 则认为数据在传输过程中**没有发生错误**。如果余数不为 0： 则认为数据在传输过程中发生了错误，通常会请求发送端重传数据。

#### PPP协议透明传输

##### PPP字节传输 异步传输

###### 为什么

PPP 帧的定界符是固定的：

标志字段 F = 0x7E（二进制 01111110）

控制转义字符 = 0x7D

如果在 数据部分 中恰好出现了 0x7E，接收方会误以为是帧的结束。
所以必须把数据中的 0x7E 转义成别的，让接收方知道这不是帧尾

###### 规则

数据中的 0x**7E** → 转义为 0x**7D 0x5E**

数据中的 0x**7D** → 转义为 0x**7D 0x5D**

1.1.1 为什么

MTU（含报头） 的限制：每种技术都有其最大传输单元 (MTU)，即它可以携带的 IP 数据报的最大字节数。一般为1500

**最大分片数据部分的=MTU-报头（IP报头20字节）**

如果题目给出的是 UDP/TCP 数据，需加上其报头 (如 UDP 8 字节, TCP 20 字节)。

如果题目给出的是 IP 数据报总长度，只需减去 20 字节的 IP 报头。

路由器检测： 当路由器收到一个 IP 数据报，发现其总长度超过了下一跳链路的 MTU 时，它必须将该数据报分割成更小的、能通过该链路的片段（即分片）。

1.1.2

**标识唯一相同**

**MF（more) 后面有分片1 最后一个0**

**片偏移：当前分片数据部分起始字节数/8**

| **字段 (Field)**             | **长度** | **作用**                                                     |
| ---------------------------- | -------- | ------------------------------------------------------------ |
| **标识 (Identification)**    | 16 位    | 原始 IP 数据报的**唯一标识**。同一个数据报的所有分片都使用**相同**的标识值 |
| **标志 (Flags)**             | 3 位     | **DF (Don't Fragment):** 设为 1 时，表示该数据报禁止分片；若超过 MTU，路由器将丢弃它  **MF (More Fragments):** 设为 **1** 表示后面**还有**更多分片；设为 **0** 表示这是**最后一个**分片。 |
| **片偏移 (Fragment Offset)** | 13 位    | 指示该分片的数据部分在**原始数据报**的数据部分中的**起始**位置。 |

1.1.3 每个分片的**数据部分**长度（不含首部）必须是**8的倍数**（8字节=64位）

### 6.ARP

![image-20260108162836861](/assets/images/study-notes/computer-network-exam-points/28-image-20260108162836861.jpg)

1.地址解析协议： 用于在局域网（LAN）中**将 IP 地址 解析为 MAC 地址（物理地址）**

ARP 是链路层协议，但为网络层服务

**ARP 请求是广播，应答是单播**

2.ARP 工作过程（举例）
假设主机 A（IP: 192.168.1.2）想给主机 B（IP: 192.168.1.3）发送数据：

A 检查 B 的 IP 是否在同一子网（是）

A 查看自己的 ARP 缓存表，看是否有 B 的 IP→MAC 映射

如果没有，A 广播一个 ARP 请求包：
“我是 192.168.1.2，MAC 是 AA:AA:AA:AA:AA:AA，谁有 192.168.1.3 的 MAC 地址？”

局域网内所有主机收到广播，只有 B 回应一个 ARP 应答包（单播）：
“我是 192.168.1.3，MAC 是 BB:BB:BB:BB:BB:BB”

A 收到应答，将 B 的 IP→MAC 存入 ARP 缓存，然后用 B 的 MAC 地址封装数据帧发送

3.在 IP 数据报转发过程中的使用次数
每次数据报要从一台设备发往下一跳设备时，如果不知道下一跳的 MAC 地址，就要用一次 ARP

ARP 只在同一局域网（同一链路） 内使用

**1（A→R1） + 5（每个路由器转发各 1 次） = 6 次**

### 5.TCP三次握手

![image-20260108181128611](/assets/images/study-notes/computer-network-exam-points/42-image-20260108181128611.jpg)

一：STN报文

A向B发连接请求报文段 SYN=1（不携带数据，消耗一个序号） seq=x

二：SYN+ACK报文

同意连接 向A发确认 SYN=1 seq=y ack=x+1(收到x,期待x+1)

三：给B发确认ACK报文(可以携带数据)

ACK=1 seq=x+1 ack=y+1

#### 为什么不是两次？

防止“已失效的连接请求”造成错误
这是最根本的原因。我们可以假设一个场景：
1. 第一次尝试：客户端 A 发出一个连接请求（SYN1）。但这个报文由于网络拥塞，在某个路由器里“迷路”了，没能及时到达服务端 B。
2. 重传：客户端 A 等不到回应，以为 SYN1 丢了，于是重新发送了一个连接请求（SYN2）。
3. 成功建立：这次 SYN2 很快到达了 B，B 回应后，双方通过两次或三次握手建立连接，传完数据后关掉了连接。
4. 意外发生：就在连接关闭后，那个“迷路”的 SYN1 突然到达了 B。
如果是“两次握手”：
• 服务端 B 收到 SYN1，以为 A 又想建立新连接，于是立刻发出确认报文。
• 连接建立成功：此时 B 认为连接已经好了，开始坐在那里等 A 发数据。
• A 的反应：A 其实并没有想建立连接，它会直接忽略 B 的这个确认。
• 结果：B 一直在空等，白白浪费了 CPU 和内存资源。
如果是“三次握手”：
• B 发出确认后，A 发现自己并没有发送这个请求，于是不予理睬。
• B 因为收不到 A 的“第三次握手”确认，就知道这个连接没建立成功，从而释放资源。
